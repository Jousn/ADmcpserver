## 2026-08-03 (星期一)

### 今日重点

原理图元件放置与移动问题的集中修复尝试，以及项目方向的重大战略调整。经过一整天对 DelphiScript 原理图编辑功能的调试仍未解决核心问题，最终决定将项目从"AI 直接操作设计"转向"AI 顾问模式 + 插件交互"架构，并开始 Skill 与插件方案的设计。

### 详细工作内容

#### 上午：库识别问题修复与元件放置调试

**功能实现**

- **库识别问题修复**：
  - 问题：`edit_schematic` 的 `place_component` action 无法在工程中找到目标库文件，导致元件放置失败
  - 解决方案：将库文件（`.SchLib`）直接安装/拷贝到工程目录中，确保 Altium 能在工程搜索路径内找到库引用
  - 验证：导入 `Miscellaneous Devices.SchLib` 后，`search_library_symbol` 和 `place_component` 均能正确识别库中的元件（如 Res1、Res2）

- **元件放置坐标问题排查**：
  - 现象：通过 `place_component` 放置元件后，元件始终出现在原理图左下角（坐标接近 0,0），而非指定的目标坐标
  - 初步分析：怀疑是 Altium API 的 `PlaceSchComponent` 函数在放置后未正确设置坐标，或坐标单位转换有误
  - 尝试方案 1：在 `PlaceSchComponent` 后增加 300ms 延迟，再通过句柄定位设置坐标 → 仍然出现在左下角
  - 尝试方案 2：两步法 — 先 `PlaceSchComponent` 放置到 (1000, 1000) mils（确保在原理图边界内），再调用 `set_component_transform` 移动到目标位置 → `set_component_transform` 移动失败，元件位置不变

**Bug 修复**

- `Undeclared identifier LoadFromLibrary` 错误：
  - 原因：DelphiScript 不支持 `LoadFromLibrary` 方法名
  - 修复：替换为 `SchObjectFactory` 创建元件，再用 `PlaceSchComponent` 放置

#### 下午：元件移动问题深度调试

**功能实现**

- **元件移动子对象问题排查**：
  - 现象：使用 `set_component_transform` 移动元件时，只移动了元件主体，Designator（位号）和 Comment（注释）等子对象未同步移动，导致元件与标注分离
  - 原始实现：使用 `SchIterator` 遍历 `eDesignator` 和 `eComment` 对象类型，分别设置其 Location 属性
  - 错误：`Undeclared identifier: eComment` — DelphiScript 中 `eComment` 枚举值不存在
  - 修复尝试：改为直接属性访问 `Comp.Designator.Location` 和 `Comp.Subpart.Comment.Location` → 编译通过，但移动后 Designator 和 Comment 虽然同步移动了，元件主体却出现异常

- **直接修改 Comp.Location 导致电阻拉伸变形**：
  - 现象：代码设置 X=1000 mils, Y=0, Rotation=0°，但执行后电阻图形被拉伸变形
  - 根因分析：直接修改 `Comp.Location` 属性会触发 Altium 内部的缩放机制，导致元件图形被意外拉伸，而非简单的位置平移
  - 修正方案：改用 `set_component_transform` action，通过 `SetState_X()` / `SetState_Y()` 方法设置坐标，避免触发缩放
  - 但 `set_component_transform` 仍然无法正确移动元件到目标位置

- **全天调试总结**：
  - 已尝试的方法：`PlaceSchComponent` + 延迟 + 句柄定位、两步法（放置+移动）、`SchIterator` 遍历子对象、直接修改 `Comp.Location`、`set_component_transform` action
  - 核心问题未解决：元件放置后出现在左下角，且无法通过任何已知 API 方法正确调整坐标到目标位置
  - 子对象同步问题：即使元件主体移动成功，Designator 和 Comment 也无法保证同步移动

**关键决策**

- 经过一整天的调试仍未取得突破性进展，结合此前在 PCB 自动布局/布线方面遇到的类似瓶颈（AI 生成结果达不到生产级别），决定进行项目方向战略调整

#### 晚间：项目方向战略调整 — Feature Flags 实施

**环境/架构**

- **核心决策**：将项目从"AI 直接操作设计"模式转向"AI 顾问模式（Advisory Mode）"，即 AI 提供设计建议和审查分析，而具体的绘图和布局操作交给 Altium 原生交互或专用插件完成
- **决策依据**：
  1. AI 在原理图元件放置和 PCB 布局方面的精度无法达到生产级别
  2. DelphiScript 通过文件桥接方式的坐标控制存在系统性缺陷
  3. AI 算力限制导致生成的电路设计质量不稳定，复杂电路（>10 元件）需要大量人工修正
  4. AI 自主绘图和布线能力有限，坐标计算误差大，引脚位置未知

**功能实现**

- **Feature Flags 三层门控机制实施**：
  - 在 `src/index.ts` 中新增三个环境变量控制开关：
    - `ENABLE_SCHEMATIC_WRITES`（原理图写入）：设为 `false`
    - `ENABLE_PCB_WRITES`（PCB 写入）：设为 `false`
    - `ENABLE_SYMBOL_CREATION`（符号创建）：设为 `false`
  - 当开关为 `false` 时，对应工具调用返回 `WRITE_OPERATIONS_DISABLED` 错误，并提示用户该功能已转为顾问模式

- **代码修改清单**：
  - `src/index.ts`：注册工具时检查 Feature Flag，禁用的工具不注册或注册后返回错误
  - `altium-scripts/Altium_API.pas`：DelphiScript 端增加开关检查逻辑
  - `src/mcpInstructions.ts`：更新指令集，说明当前为顾问模式，7 个写入工具已禁用

#### 下午：库元件记忆去重机制重构

**环境/架构**

- 此前库元件记忆文件采用简单的追加写入方式，每次导入库元件都会生成新的 `MEM:LIB_CATALOG` 条目，导致重复元件堆积、记忆文件膨胀、检索效率下降

**功能实现**

- **去重机制设计与实现**：
  - 重写 `src/index.ts` 中的 `writeShortTermCatalog()` 函数：
    - 导入时先解析现有目录，以 `lib_reference` 为主键建立索引
    - 新元件：追加到目录末尾
    - 已存在元件（同库）：更新描述/封装/位号信息
    - 跨库重复元件：合并 `sources` 字段，保留多个库来源记录
  - 重写 `parseExistingCatalog()` 函数：
    - 支持解析带 `sources` 字段的 KB 格式表格
    - 正确跳过空行和表头
  - 在 `src/memoryManager.ts` 的 `CachedComponent` 接口中新增 `sources` 字段：
    ```typescript
    interface CachedComponent {
      lib_reference: string;
      description: string;
      footprint: string;
      part_count: number;
      designator: string;
      sources: string[];  // 新增：记录元件来源的库文件列表
    }
    ```
  - 更新 `docs/memory-persistence-guide.md`：补充去重机制说明

- **KB 格式解析器 Bug 修复**：
  - 问题：`memoryManager.ts` 中的 KB 格式解析器在解析知识库表格时，无法正确跳过空行和表头行，导致解析结果包含垃圾数据
  - 修复：新增 `skipTablePrefix()` 辅助函数，在解析表格行前先检测并跳过 `|---|` 分隔行和空行
  - 验证：重新导入库元件后，解析结果干净无冗余

**验证**

- **去重效果验证**：
  - 测试场景：首次导入 → 同库重复导入 → 跨库导入
  - 首次导入 `Miscellaneous Devices.SchLib`：195 个元件
  - 重复导入同一库：元件数不变，`sources` 不变（同库去重生效）
  - 跨库导入 5 个库后：380 个唯一元件（原始 575 个，去重率 34.0%）
  - MCP 服务器重启后重新运行 `import_library_components`，确认工具行为与记忆文件一致
