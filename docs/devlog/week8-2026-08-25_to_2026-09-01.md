## 阶段背景

本周目标从"工具可用"推进到"AI 能画对电路"。以晶体管无稳态多谐振荡器 LED 闪烁电路为测试载体，暴露并修复了一整条链路上的问题：元件放置 → 引脚坐标读取 → 导线连接 → 连接性验证。

## 1. place_component 修复（从 NOT SUPPORTED 到可用）

### 1.1 根因

Week7 中 place_component 因 SchObjectFactory 创建"空壳元件"（无引脚/无封装）被禁用。本周找到正确路径：调用 Altium 内置进程 `IntegratedLibrary:PlaceLibraryComponent`，由库服务器完成完整元件实例化。

### 1.2 实现

- `schematic_edit.pas`：通过 `RunProcess` 调用 `IntegratedLibrary:PlaceLibraryComponent`，参数为 Library Name / Library Reference / Location X / Location Y / Orientation
- 放置后回读校验：位号、坐标、引脚数、参数（Value / PackageReference）
- 实测：Miscellaneous Devices.IntLib 的 Res1 完整落地，R1 @ (5000, 3000)，2 引脚，Value=1K, PackageReference=AXIAL-0.3

## 2. 引脚电气热点（hotspot）计算

### 2.1 问题

元件引脚自带一段导线延伸（pin length，100mil 或 200mil 不等）。导线不能连在引脚根部，必须连到引脚**自由端**（电气热点），否则不导通。`get_component_info` 原先返回的坐标不能直接用于布线。

### 2.2 实现

`schematic_edit.pas` 新增热点计算：

- 引脚朝向枚举（eRotate0/90/180/270）→ 旋转角度映射
- 元件整体旋转角 + 引脚局部朝向 → 热点方向
- 热点坐标 = 引脚坐标 + PinLength × 朝向单位向量

### 2.3 修复过程中的两个编译错误（经验沉淀）

| 报错 | 根因 | 修复 |
|------|------|------|
| undeclared identifier: Length (L1645) | 引脚长度属性为 `PinLength`，API 文档笔误写成 Length | 改用 `Pin.PinLength`，代码注释标记文档笔误 |
| undeclared identifier: Integer (L1658) | DelphiScript 不支持 `Integer()` 强制类型转换枚举 | 改用 `case` 语句将枚举映射为角度字符串 |

**教训：创建新代码必须参考标准库（scripting-reference-master）真实代码，不凭空捏造参数——API 文档本身也会有笔误。**

## 3. delete_object 工具（纠错闭环）

布线出错后需要删除错误对象重画。基于 `RemoveSchObject` 实现 `delete_object`，支持删除元件/导线等对象，与 place_component / add_wire 构成完整的"放置 → 检查 → 删除重放"纠错流程。

## 4. LED 闪烁电路实测与提示词工程

### 4.1 实测暴露的问题

AI 绘制 LED 闪烁电路（2×NPN + 2×LED + 2×电解电容 + 4×电阻）时出现系统性连线错误：

1. **导线穿过元件短路**：垂直放置的 2 引脚元件（如旋转 90° 的 Res1）两引脚在同一 x 坐标上下排列，长垂直导线穿过元件同时碰到两个热点，把元件短路
2. **旋转后引脚坐标失效**：元件旋转后仍用旧坐标连线
3. **T 接点无结点**：导线搭在另一导线中段未加 junction
4. **电源端口位置偏差**：GND/VCC 端口放在导线附近而非精确落点

### 4.2 提示词改进（mcpInstructions.ts）

新增布线规则：

- **R5. TERMINATE AT ONE PIN**（2 引脚元件关键规则）：导线只连接它终止的那个引脚。禁止一条导线穿过元件碰到同一元件的第二个引脚。正确做法：导线停在第一个（近端）引脚，路径从元件另一端引脚用新导线继续
- **R6. JUNCTIONS**：3+ 导线交汇点（含 T 接点）必须 add_junction

新增验证硬门禁（HARD GATE）：

- 布线后强制调用 `check_connectivity` 机器审计，`ok=true + pins_floating=0` 才能保存
- 禁止仅凭工具调用成功率宣称"100% 成功"——工具成功只代表对象创建了，不代表连通了

## 5. check_connectivity 审计工具（本周核心交付）

### 5.1 双层架构

| 层 | 数据源 | 角色 |
|----|--------|------|
| 权威层（compiled-dm） | Altium 编译器 DM 数据（`Project.DM_Compile` → `Pin.DM_FlattenedNetName`） | 短路/浮空判定（编译器本身解析导线/结点/T接点/电源端口/网络标签语义） |
| 几何层（supplement/fallback） | get_schematic_data 几何数据 + 引脚热点 | 检测编译器不报的问题（悬空线头/标签不落线/T接点缺结点）；DM 层不可用时回退 |

### 5.2 Pascal 端（schematic_utils.pas）

新增 `CheckSchematicConnectivityData`，**全部 DM API 逐项核对官方 Connectivity.pas 示例**（scripting-reference-master）：

| API | 参考来源 |
|-----|---------|
| Project.DM_Compile | Connectivity.pas L292 |
| DM_PhysicalDocumentCount / DM_PhysicalDocuments(J) | L217-218 |
| Doc.DM_ComponentCount / DM_Components(J) | L171-173 |
| Comp.DM_SubPartCount / DM_SubParts(n) | L175, L190 |
| Pin.DM_PinNumber / DM_FlattenedNetName | L181 |
| '?' 网络名 = 未连接引脚 | L194 |

输出每引脚 JSON 行：`{designator, pin, net, unconnected}`。与官方示例的差异：多部件元件的 '?' 引脚也保留（审计需要，官方示例跳过）。

### 5.3 Node 端（src/tools/checkConnectivity.ts）

- `analyzeConnectivity(input)`：DM 权威模式（按编译网络名分组）+ 几何回退模式（联合查找 Union-Find 聚类）
- 几何聚类语义：导线端点落在另一导线上 = 连通；纯 X 交叉不连通；junction 使交叉连通

检测项：

| 类型 | 代码 | 说明 |
|------|------|------|
| 错误 | SHORT_ACROSS_COMPONENT | 一条导线短路元件（R5 bug 的机器检测；多引脚 IC 共享电源网络（如双 GND 引脚）合理放行） |
| 错误 | POWER_NET_SHORT | VCC/GND 等不同电源网络被合并 |
| 错误 | FLOAT_PIN | 引脚悬空（编译器报 '?' 网络） |
| 错误 | NET_NAME_SHORT | 回退模式：不同命名网络聚为一簇 |
| 警告 | T_CONTACT_NO_JUNCTION | T 接点缺结点 |
| 警告 | DANGLING_WIRE_ENDPOINT | 悬空线头 |
| 警告 | LABEL_NOT_ON_WIRE | 网络标签不落线（无效） |

报告输出 `nets[]`（每个网络的引脚成员表），可与 R0 引脚覆盖表比对。

### 5.4 注册与集成

- `index.ts`：注册工具，先取 DM 层（240s 超时，失败自动回退几何模式），再取几何数据，合成审计报告
- `toolDefinitions.ts`：DESCRIPTION_CHECK_CONNECTIVITY
- Altium_API.pas：命令分发 `check_connectivity` → ExecuteCheckConnectivity

## 本周经验沉淀

1. **以官方示例为准，不以文档为准**：`Pin.Length`（文档笔误）vs `Pin.PinLength`（Connectivity.pas 等真实代码）——新代码一律先在 scripting-reference-master 找同名 API 用法
2. **DelphiScript 语法限制**：无 `Integer()` 强转、枚举用 `case` 映射、`&&` 在 PowerShell 中不可用（用 `;`）
3. **工具调用成功 ≠ 电路正确**：必须机器审计（编译器 DM 数据）作为 HARD GATE，提示词约束（R5）只能降低概率，不能替代验证
4. **文件句柄生命周期**：重试循环中"条件打开 + 无条件关闭"是双重关闭 bug 的典型模式；打开/关闭应在同轮迭代内配对
