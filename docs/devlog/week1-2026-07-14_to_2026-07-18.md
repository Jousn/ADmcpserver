# Altium Designer MCP 接入 AI 大模型 — 开发日志（第一周）

> 项目名称：altium-mcp
> 技术栈：Node.js 20+ / TypeScript 5.8 / @modelcontextprotocol/sdk 1.29 / Zod 3.24 / DelphiScript
> 开发周期：2026-07-14 ~ 2026-07-18

## 2026-07-14 (星期二)

### 今日重点

完成项目立项调研与上游仓库选型，确定基于 MCP 协议的 JSON 文件桥接架构，fork 上游项目 `flaco-source/altium-mcp` 作为开发基线。

### 详细工作内容

**环境/架构**

- 调研 Altium Designer 的自动化能力边界。确认 Altium 仅支持通过 DelphiScript 脚本自动化，无 HTTP/RPC 接口，必须使用文件作为进程间通信媒介。
- 对比三种 AI-EDA 桥接方案：Socket/Named Pipe、COM 自动化、JSON 文件桥接。最终选择 JSON 文件桥接代理模式（Layered + Bridge Agent），核心权衡是 Altium 的 DelphiScript 环境对网络 API 支持有限，文件方案换来零依赖、易调试、崩溃隔离三大优势。
- 配置本地开发环境：Node.js 20、TypeScript 5.8、Vitest 3.1、Git。
- Fork 上游仓库 `flaco-source/altium-mcp`（MIT 许可，源自 `coffeenmusic/altium-mcp`），clone 到本地工作目录。

**功能实现**

- 确认上游仓库初始提交（`0210f19`）已包含 43 个文件、10140 行代码的完整骨架，涵盖：MCP 服务器 TypeScript 实现（`src/`）、DelphiScript 桥接脚本（`altium-scripts/`，7 个 .pas 文件）、CI/CD（`.github/workflows/ci.yml`）、文档体系、Vitest 测试。
- 梳理上游已注册的 13 个 MCP 工具：3 个 Node 本地工具（`get_server_status`、`configure_altium_exe`、`file_mode_capabilities`）+ 10 个桥接工具（`altium_ping`、`get_workspace_projects`、`get_schematic_data`、`edit_schematic`、`get_pcb_layers`、`get_pcb_rules`、`get_all_nets`、`get_pcb_layer_stackup`、`get_all_designators`、`get_component_pins`）。

**技术决策**

- 选择在上游 fork 基础上二次开发，而非从零构建。原因：上游已实现核心桥接通信机制（`AltiumBridge` 类、文件锁 `withBridgeLock`、脚本包同步 `ensureAltiumScriptBundle`），且 DelphiScript 脚本经上游验证可用，可节省 1-2 周基础架构搭建时间。
- 保留 MIT 许可证，在 `NOTICE` 文件中标注上游来源。

### 明日计划

通读上游 `src/` 与 `altium-scripts/` 全部源码，建立项目四层架构心智模型。

## 2026-07-15 (星期三)

### 今日重点

通读上游核心源码，理解 `AltiumBridge.executeCommand()` 的完整 9 步调用链与 DelphiScript 端的命令分发机制。

### 详细工作内容

**环境/架构**

- 绘制项目分层架构图，确认四层职责边界：
  - **接口层**（`src/index.ts`、`src/toolDefinitions.ts`、`src/mcpInstructions.ts`）：注册 MCP 工具，参数校验与转发
  - **桥接层**（`src/bridge/altiumBridge.ts`、`src/bridge/lock.ts`、`src/workspaceLayout.ts`）：JSON 文件通信、进程启动、文件锁
  - **校验层**（`src/tools/editSchematic.ts`、`src/tools/getSchematicData.ts`）：Zod Schema 定义
  - **执行层**（`altium-scripts/*.pas`）：DelphiScript 调用 Altium API

**功能实现**

- 分析 `AltiumBridge.executeCommand()` 的 9 步调用链：获取锁 → 同步脚本 → 检查 EXE → 写 `request.json` → 启动 Altium → 轮询 `response.json`（500ms 间隔，默认 120s 超时，`edit_schematic` 为 240s）→ Schema 校验 → 返回结果。
- 分析 `altium_API.pas` 的 `Run` 过程：读取 `request.json` → 逐行解析 command 参数 → `ExecuteCommand` case 分发 → `WriteResponse` 写入 `response.json`。检测 `ERROR:` 前缀自动设置 `success=false`。
- 分析 `schematic_edit.pas`（1053 行），确认其实现 11 种 action 分发：`set_component_transform`、`set_component_parameters`、`place_component`、`add_text`、`add_net_label`、`place_net_label`、`add_wire`、`place_wire`、`add_bus`、`add_bus_entry`、`place_power_port`/`place_gnd`/`place_vcc`。

**Bug修复**

- 发现上游 `docs/ts-pas-command-comparison.md` 中统计有误：文档声称 TS 注册 13 个工具、PAS 支持 23 个命令、13 个 PAS 命令未注册。实际核验 `src/index.ts` 后确认此为**当前项目改造前的历史文档**，上游实际仅注册了 10 个桥接工具。

**技术决策**

- 确定后续开发方向：以上游 23 个 PAS 命令为能力底座，将未注册的 13 个命令逐步注册为 MCP 工具，并补充文档与测试。

## 2026-07-17 (星期五)

### 今日重点

系统梳理两个脚本版本中的 Altium Designer API 接口，编写 API 参考文档，并生成功能对比分析。

### 详细工作内容

**功能实现**

- 分析 `altium-scripts/` 目录下 7 个 DelphiScript 文件中引用的 Altium Designer API 接口，按功能分类：
  - **PCB 接口**：`IPCB_Board`、`IPCB_Component`、`IPCB_Net`、`IPCB_Layer`、`IPCB_Rule`、`IPCB_Pad`、`IPCB_Track`、`IPCB_Arc`、`IPCB_Fill`、`IPCB_Via` 等
  - **原理图接口**：`ISch_Document`、`ISch_Component`、`ISch_Pin`、`ISch_Wire`、`ISch_Bus`、`ISch_BusEntry`、`ISch_NetLabel`、`ISch_PowerObject`、`ISch_Text`、`ISch_GraphicalObject` 等
  - **工作区/文档接口**：`IWorkspace`、`IDocument`、`ISch_Library`、`IPCB_Library` 等

- 创建 `docs/altium-api-reference-scripts.md`（实际使用版，113 个唯一接口）和 `docs/altium-api-reference-main.md`（Python 参考实现版，77 个唯一接口）。
- 编写 Python 分析脚本 `analyze_interfaces.py`，自动提取接口引用并生成对比报告。

**Bug修复**

- 初始编写 API 文档时误将第二份文档覆盖了第一份。发现后立即从备份恢复，并为两份文档使用不同的文件名（`-scripts.md` 与 `-main.md`），在文档头部添加明确的目录来源标注。
- `analyze_interfaces.py` 初次运行报 `KeyError: 'Other'`，添加 `'Other': []` 到分类字典后修复。

**技术决策**

- 两份文档分开维护而非合并，因为两个版本的接口集合差异显著（实际版 113 个 vs 参考版 77 个，仅 70 个共有），合并会丢失版本差异信息。
- 确认后续开发以 `altium-scripts/`（实际使用版）为准，因为它的接口覆盖面更广、原理图编辑能力更完整。

### 明日计划

梳理当前 TS 脚本中已注册工具与 PAS 桥接命令的对应关系，识别未注册的命令并制定补全计划。
